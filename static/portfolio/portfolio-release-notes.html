How an iterative collaboration with Claude transformed a slow, error-prone, manual process into a fully interactive release management tool — complete with domain intelligence, cross-release search, and Outlook-ready email drafting.

📅 Recurring Weekly Workflow 🔗 Azure DevOps Integration 📧 Outlook Automation ⚡ Built Iteratively with Claude
The Problem

Release Notes Were Slow, Manual, and Easy to Get Wrong

Every Tuesday, the DataMarketplace team ships a release to production. Before each deployment, someone has to compile release notes and distribute them to over 30 stakeholders. What sounds simple was anything but.

🖱️

Lots of Clicking

Generating release notes meant navigating ADO, opening each work item individually, and manually copying fields into a Word document — story by story.

🔀

Constant Tab Switching

Cross-referencing ADO, SharePoint, Outlook, and the release notes template required constant context-switching. Easy to lose your place, easy to miss items.

🗂️

Inconsistent Domain Classification

Bucketing items into the correct business domain required manual knowledge of which gold tables belong to which product area — a task that was inconsistently applied.

📧

Manual Email Composition

After building the notes, you still had to format them, compose a time-sensitive greeting, recall 30+ recipient addresses, and send — every single week.

🔍

No Search Across History

Answering "when did we last change anything Anaplan-related?" required scrolling through months of SharePoint documents with no structured way to search.

⏱️

Disproportionate Time Cost

A task that should take 10 minutes regularly consumed 30–45 minutes of a Product Owner's time — and that was before any interruptions or off-schedule releases.

The core insight: The information already existed in ADO. The problem wasn't access to data — it was the absence of a purpose-built tool that assembled it, classified it, and put it in the right format for the right audience.

The Build

An Iterative Journey from Query to Product

The tool didn't start as a grand design. It started as a single question to Claude about what was going to production that day — and grew from there through a series of deliberate, compounding iterations.

Phase 1 · Discovery
The First Query
Started by asking Claude a simple ADO question: "Which items are scheduled to go to production today where I'm the product contact?" Claude used the existing ADO skill to fetch the answer directly — no tab-switching, no manual filtering. The immediate value of having an intelligent intermediary between the user and raw API data was clear.
ADO WIQL First prototype
Phase 2 · MVP
"Let's Build a Release Notes Generator"
The first request to create something real: a web-based app with a release calendar, work item list, and a formatted output. Claude generated a full-featured HTML application with embedded JavaScript making live ADO API calls — all in a single file. The browser became the interface; ADO became the data source.
Dynamic HTML app ADO REST API WIQL queries
Phase 3 · Intelligence
Domain Classification from SharePoint Source of Truth
The release notes required bucketing items by business domain. Rather than hard-coding guesses, Claude was directed to the authoritative source — Data Domains.xlsx in SharePoint. The app now embeds an 87-entry table → domain mapping with longest-match logic, source system overrides (Salesforce→Property, Anaplan→Financial Corp), and valid domain validation against the official col D list.
SharePoint integration Domain classification Business rules encoding
Phase 4 · Communication
Outlook Integration and Email Automation
Added a full email management system: a 31-person distribution list with bulk Outlook paste import, a rich HTML email generator matching the manual Greystar format (with time-aware greeting, DLT pipeline date calculation, and Calibri-styled bullet hierarchy), and a one-click Open in Outlook that pre-fills recipients and subject — with rich HTML pre-copied to clipboard for immediate paste.
Outlook mailto integration Rich HTML clipboard Email template engine
Phase 5 · Discoverability
Cross-Release Search with Calendar Highlighting
Added the ability to search across all past and upcoming releases by keyword. Results group by release ID, highlight matching terms, and visually mark those dates on the calendar with amber outlines — making it trivial to answer "when did we last touch anything related to Anaplan?" or "show all releases containing StarRez."
Cross-release search Calendar intelligence WIQL CONTAINS
Phase 6 · Architecture Evolution
From Browser Fetch to MCP-Routed Claude App
Direct ADO REST calls from the browser were blocked by a corporate network proxy. The solution: route all ADO queries through Claude's MCP tools via the Anthropic API. The app now sends natural language prompts to Claude, which calls ado:ado_wiql_query and ado:ado_batch_fetch on behalf of the UI — eliminating the proxy problem entirely while keeping all UI logic, domain classification, and formatting intact.
Anthropic API MCP tool orchestration Proxy-resilient architecture
Phase 7 · Reusability
Codified as Skills for the Team
The patterns developed through iteration were distilled into reusable Claude skills: a project-agnostic ADO Backlog Analyst (any org, any project, prompt-based PAT) and a DMP Release Notes skill encoding the full formatting spec, domain map, distribution list, and email template — so any team member can generate release notes conversationally without opening the app.
Skill creation Knowledge transfer Reusable patterns
What Got Built

A Central Release Intelligence Hub

Six major capability areas, each addressing a distinct pain point from the original manual process.

📅

Release Calendar

Visual calendar with Tuesday release days highlighted. Green dots mark confirmed ADO releases. Amber outlines show search matches. Default view auto-selects the current week's release — or next Tuesday if it's Friday through Sunday.

🗂️

Automatic Domain Classification

Each work item is classified against an 87-entry gold table → domain lookup sourced from the authoritative Data Domains SharePoint spreadsheet. Longest-match wins; source system overrides handle Yardi, Salesforce, Anaplan, Oracle, and more.

📋

Formatted Release Notes

Generates the exact release notes document format matching the Greystar template: correct section headings based on product group span, alphabetical domain sorting, four-bullet item hierarchy, and Infrastructure Changes bucketing for Reference Data.

✉️

Outlook-Ready Email

Produces a rich HTML email matching the manual Greystar format. Time-aware greeting, DLT pipeline date calculation, domain-bucketed content with correct bullet hierarchy. One click copies to clipboard; another opens Outlook with recipients and subject pre-filled.

🔍

Cross-Release Search

Search across all POApproved DMP items by keyword in real time. Results group by release, highlight matching terms, and mark all matching dates on the calendar — making historical impact analysis instant.

👥

Distribution List Management

Persistent email recipient list with individual add/remove, bulk Outlook paste import (Name <email> format), and duplicate detection. Works across sessions via localStorage.

On the ReleaseNotes field: During development it was discovered that Custom.ReleaseNotes in ADO contains internal DevOps deployment instructions — not business-facing content. The field was explicitly excluded from all data fetches and output paths, and a prohibition was encoded into the Claude system prompt to prevent it from ever appearing in stakeholder-facing output.

"The most time-consuming part used to be the domain bucketing and formatting. Now I load the release, verify the classifications, click send. What took 45 minutes is under 5."

— Will Yoste, Technical Product Owner, Greystar DataMarketplace

Learning Points

What This Project Taught

Each iteration surfaced something new — about Claude's capabilities, about browser-based application architecture, and about how to think about AI-assisted product development.

01

ADO as a Data API, Not Just a UI

Azure DevOps has a powerful REST API with WIQL — a SQL-like query language for work items. Treating ADO as a proper data source rather than a UI to click through unlocks automation that the native interface never enables. Building WIQL queries iteratively (and learning that square brackets break them) was a foundational skill.

02

Dynamic HTML Apps Are Underrated

A single HTML file with embedded JavaScript can be a fully functional, distributable application. No deployment pipeline, no hosting cost, no framework overhead. The browser becomes the runtime. For internal tools serving a small team, this is often the right architecture — especially when the alternative is a SharePoint form or a weekly spreadsheet.

03

Iterative Prompt Development

The prompt engineering here wasn't a one-shot spec — it was iterative refinement based on observed failures. Discovering that Custom.ReleaseNotes was leaking into output, then encoding that prohibition into the system prompt, is a concrete example of how prompt development mirrors software development: test, observe failure, fix, re-test.

04

Microsoft Outlook Integration via Web Standards

Integrating with desktop Outlook from a web page requires two steps that aren't obvious: copy rich HTML to the clipboard using the ClipboardItem API (so paste in Outlook preserves formatting), then open Outlook via a mailto: link. The combination creates a seamless handoff without requiring any Outlook add-in or COM automation.

05

Network Architecture Matters

Direct browser-to-ADO REST calls work in development but break behind a corporate proxy. Rearchitecting to route data through the Anthropic API → MCP tools solved the proxy problem while also making the tool authentication-agnostic. This pattern — using Claude as a trusted intermediary — is broadly applicable to enterprise tooling.

06

Business Logic Belongs in the Data Layer, Not the Presentation Layer

Early versions of domain classification were ad hoc. Moving to a structured lookup table sourced from SharePoint's authoritative Data Domains spreadsheet made the logic auditable, correctable, and consistent. When the domain list changes, there's a clear single place to update — a principle that applies well beyond this specific tool.

07

Skills as Reusable Institutional Knowledge

Distilling the tool's logic into Claude skills meant the work didn't stop at "we have an app." The domain map, ADO query patterns, email format, and distribution list are now captured as reusable prompts that any team member can invoke conversationally — turning individual learning into organizational capability.

08

Finding the Right Use Case Is the Hard Part

The release notes workflow succeeded as an AI product because it had the right ingredients: high-frequency recurrence, clear input data (ADO), well-defined output format (the Greystar template), and a measurable time cost. Not every workflow meets these criteria. The judgment of which problems to automate matters more than the automation itself.

The meta-lesson: The best use cases for AI-assisted tooling are recurring, structured tasks where the data already exists, the output format is well-defined, and the manual version is tedious rather than genuinely difficult. The release notes process was a perfect specimen of exactly this kind of problem.
